# 맘편하게 (Mompeace)

임신 중 식품 섭취를 더 안심하고 결정할 수 있도록 돕는 모바일 앱입니다.

식품을 검색하거나 영양성분표를 촬영하면, **오늘 하루 누적 섭취량(카페인·당류·나트륨)**과 **임신 주차**를 함께 고려해 해당 식품을 **섭취 가능(possible) / 주의(caution) / 비추천(avoid)** 중 하나로 안내합니다.

같은 음식이라도 아침에 먹을 때와 이미 커피를 두 잔 마신 오후에 먹을 때의 답이 달라야 한다는 것이 이 앱의 출발점입니다.

## Core Features

- **식품 안전 판정** — 영양성분표 OCR 스캔 또는 검색으로 식품을 찾으면, 오늘 누적 섭취량과 임신 주차를 기준으로 섭취 가능 여부를 판정합니다.
- **커피 카페인 계산기** — 프랜차이즈 브랜드별 메뉴와 홈메이드 커피의 카페인 함량을 제공합니다. 모든 수치에 출처(브랜드 공식 자료 / 정부 측정값 / 교차검증된 보도)와 검증일을 함께 기록했고, 신뢰할 수 있는 출처가 없는 조합은 추정값을 넣는 대신 아예 데이터를 두지 않았습니다.
- **푸드 다이어리** — 하루/주간 단위로 누적 섭취 패턴을 확인합니다.
- **수분 다이어리** — 하루 목표 대비 수분 섭취량을 기록합니다.
- **대체 식품 추천** — 주의·비추천 식품에 대해 같은 분류에서 더 나은 대안을 제시합니다.
- **건강 리포트** — 일간·주간 섭취 분석을 제공하고, 이미지로 저장할 수 있습니다.

## Architecture

### 판정은 규칙 엔진이 한다

식품 안전 판정은 **공식 가이드라인 기반 규칙 엔진**이 담당합니다. 기준값은 ACOG, WHO, 한국인 영양소 섭취기준(KDRI) 등 공식 자료를 참고해 설계했으며, 모든 임계값은 `backend/nutrition_constants.py` 한 곳에만 존재합니다. 같은 숫자가 두 곳에 있으면 반드시 어긋나기 때문입니다.

머신러닝(RandomForest)을 합성 라벨로 학습시켜 1차 판단에 쓰는 방식도 시도했지만, 합성 라벨 자체가 규칙으로 만들어진 것이라 모델이 실질적인 신호를 더하지 못한다는 점을 확인하고 제거했습니다. 현재는 규칙 엔진이 단독으로 판정하며, 실사용자 데이터가 쌓이면 그 데이터를 활용한 개인화를 2단계로 추가할 계획입니다.

### LLM은 읽고 쓸 뿐, 결정하지 않는다

Gemini는 세 곳에서 쓰입니다. 영양성분표 이미지에서 값을 **추출**하고, 제품명을 카테고리로 **분류**하고, 이미 내려진 판정을 **설명**합니다. 어느 경우에도 안전 여부를 판단하지 않습니다.

이 경계는 프롬프트 문구가 아니라 구조로 강제됩니다.

- LLM에는 이미 계산이 끝난 결과값만 전달됩니다. `한도 − 섭취량` 같은 뺄셈조차 Python에서 수행합니다.
- 참고 자료로 주는 지식 베이스에는 **숫자가 하나도 들어있지 않습니다.** 자료에 적힌 낡은 수치가 앱의 기준값을 덮어쓰는 일을 원천 차단하기 위해서입니다.
- LLM 호출은 실패해도 앱이 멈추지 않습니다. API 키 누락, 쿼터 초과, 네트워크 오류 등 모든 실패는 규칙 엔진이 생성한 메시지로 대체됩니다.
- OCR로 읽어온 숫자도 규칙 엔진이 처음부터 다시 판정합니다.

### 임신 주차와 트라이미스터

임신 주차는 가입 시 입력한 값을 정적으로 저장하지 않고, 입력 시점(`pregnancy_entered_at`) 기준 경과일을 매 요청마다 계산합니다. 12주에 가입한 사용자가 한 달 뒤에 앱을 열면 자동으로 16주 기준으로 판정되며, 트라이미스터 경계도 스스로 넘어갑니다.

트라이미스터는 **에너지·단백질 목표치**에 반영됩니다 (중기 +340kcal·+15g, 후기 +450kcal·+30g).

반면 **카페인·당류·나트륨의 일일 허용치는 트라이미스터와 무관한 단일 기준**을 사용합니다. 이것은 구현 누락이 아니라 근거에 따른 결정입니다.

- **카페인 200mg/일** — ACOG/WHO 기준
- **당류 50g/일** — WHO 기준. KDRI는 당류의 생애주기별 차등 근거가 불충분하다고 명시합니다.
- **나트륨 2,300mg/일** — KDRI 만성질환위험감소섭취량(CDRR). ACOG·WHO·Cochrane 모두 나트륨 제한이 임신중독증 예방에 효과가 있다는 근거가 불충분하다고 보고 있습니다.

나트륨은 KDRI가 성격이 정반대인 두 기준을 제시합니다. 충분섭취량(AI) 1,500mg은 "최소 이만큼은 섭취하라"는 하한이고, CDRR 2,300mg이 상한입니다. 이 앱의 모든 판정이 "넘으면 위험"의 형태이므로 하한 기준을 상한으로 쓰면 정상적인 식단도 위험으로 표시하는 오류가 됩니다. CDRR을 채택한 이유입니다.

트라이미스터별 차이는 대신 **안내 문구**에 반영됩니다 (초기 입덧, 중기 철결핍, 후기 부종 등).

### 정보 없음과 0은 다르다

영양소 정보가 없는 음식과 실제로 함량이 0인 음식을 명확히 구분합니다. 안전을 다루는 앱에서 "측정되지 않음"을 0으로 처리하면 불확실성이 거짓 안전 신호로 둔갑하기 때문입니다.

이 원칙은 한 번의 검사가 아니라 모든 계층에 걸쳐 구현되어 있습니다.

- **저장 시점** — 과거 버전이 0으로 잘못 기록한 카페인 값을 NULL로 되돌리는 보정을 수행합니다.
- **집계 시점** — 합계와 함께 "실제로 값이 있던 행의 수"를 같이 셉니다.
- **판정 시점** — 오늘 무언가 기록됐는데 이 영양소만 한 번도 측정된 적 없으면 `unknown`을 반환합니다. 아무것도 안 먹은 날은 unknown이 아니라 그냥 비어있는 날입니다.
- **표시 시점** — 합계가 0이면 "0"이 아니라 "정보 없음"으로 노출합니다.
- **연산 시점** — 모든 곱셈과 단위 변환이 NULL을 보존합니다.
- **정렬 시점** — 값이 없는 항목은 정렬 방향과 무관하게 항상 뒤로 보냅니다.

카페인 가드를 도입하기 전 측정한 수치로, **"섭취 가능" 판정의 84%가 카페인이 한 번도 측정된 적 없는 음식에 내려지고 있었습니다.**

## Tech Stack

**백엔드** — FastAPI · SQLite · Python · bcrypt · google-genai
**프론트엔드** — React Native (Expo) · expo-router · expo-camera · react-native-reanimated · react-native-svg · expo-media-library · react-native-view-shot
**외부 서비스** — Gemini (영양성분표 OCR, 카테고리 분류, 리포트 요약)
**식품 데이터** — 공공데이터포털(data.go.kr)의 식품영양성분 데이터를 오프라인으로 가공해 로컬 DB(`food_items`)로 사용합니다. 런타임에 외부 식품 API를 호출하지 않습니다.
**디자인** — Figma

## Getting Started

### 사전 준비

프로젝트 루트에 `.env` 파일을 만들고 Gemini API 키를 설정합니다. `.env.example`을 참고하세요.

```bash
cp .env.example .env
# GEMINI_API_KEY=... 입력
```

키가 없어도 앱은 동작합니다. OCR과 AI 요약만 비활성화되고, 나머지 기능과 모든 안전 판정은 규칙 엔진이 그대로 수행합니다.

### Backend

```bash
cd mompeace  # 프로젝트 루트 (backend/ 폴더가 아님)
pip install -r backend/requirements.txt
uvicorn backend.main:app --reload
```

같은 네트워크의 휴대폰(Expo Go)에서 접속하려면 `--host 0.0.0.0`을 붙입니다.

```bash
uvicorn backend.main:app --reload --host 0.0.0.0 --port 8000
```

### Frontend

```bash
cd app
npm install
npx expo start
```

### 테스트

```bash
pytest backend/
```
